- **Upstream Synchronization** - Rebased the eleven active fork patch branches onto upstream `main` at `f2160cf08`, which carries transport `v2.5.1`. `v2.5.0-oss` was never tagged, so this is the first fork release since `v2.4.0-oss` and also carries the fork changes listed below.
- **Typed Provider Request Bodies** - SiliconFlow, DeepInfra, Z.AI and Zhipu now pass their concrete request types to upstream's generic request-body builder. A request a converter could not build is therefore rejected cleanly instead of panicking on a nil body. The Z.AI/Zhipu chat converter goes through the interface-typed builder, and the OpenAI-compatible providers keep upstream's typed path unchanged.
- **Stream Panic Recovery** - The SiliconFlow and DeepInfra speech streams recover from panics the same way upstream's provider streams now do. A panic ends the stream with a terminal error chunk instead of crashing the gateway.
- **OpenCode Session Affinity** - The OpenCode session patch (upstream PR #7052 by @sstreichan, plus the fork's credential-scoping fixes) is now its own patch branch, `feat/opencode-session-affinity`. OpenCode Go and Zen calls send a resolved `x-opencode-session` on unary and streaming Chat and Responses requests, namespaced by the authenticated virtual key or user rather than the raw gateway credential.
- **WebSocket Responses Routing** - Routing rules on the WebSocket Responses path read the upgrade headers from upstream's shared session context and add the upgrade query for `params[...]` rules. The per-session key pin now runs after routing, so it is checked against the provider and model the turn actually reaches.
- **Responses-to-Chat Compatibility** - The `compat.convert_responses_to_chat` migration runs after upstream's newest configstore migrations.
- **Provider Key Placeholders** - Z.AI and Zhipu keep their own API key placeholders in the translated key form; other providers use upstream's localized placeholder.
- **Release Source Guard** - The fork sync workflow only cuts `vX.Y.Z-oss` from a branch whose `transports/version` is `X.Y.Z`, and takes a `release_source` input to re-release an older tag from a preserved branch such as `release/v2.4.0-oss`.
- **Multinode Patch Isolation** - The optional PostgreSQL revision/CAS configuration-sync patch is still excluded from this integration and kept separately on `feat/oss-multinode-config-sync`.
