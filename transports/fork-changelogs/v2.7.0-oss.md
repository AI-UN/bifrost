- **Upstream Synchronization** - Rebased the thirteen active fork patch branches onto upstream `main` at `b437a23df`, which carries transport `v2.7.0` (4 commits past the `transports/v2.7.0` tag).
- **Anthropic Tool Stream Order** - When gateway tool search is active, Anthropic streams emit buffered client tool blocks before the `message_delta` stop reason, and stops from internal tool-search turns are suppressed (upstream issue #10370, not yet fixed upstream).
- **Responses-to-Chat Compatibility** - The `compat.convert_responses_to_chat` migration runs after upstream's new MCP client-credentials, AWS SigV4, OAuth flow-origin and notification migrations.
- **Provider Registration** - SiliconFlow, DeepInfra, Z.AI, Zhipu and CPA stay registered in every shared provider list, including the job-accounting video provider allowlist and the config and Helm schema enums.
- **Log Migration Tool** - `cmd/migratelogsobjectstorage` tracks core `v1.17.0` / framework `v1.14.0`, so it still builds standalone.
- **Multinode Patch Isolation** - The optional PostgreSQL revision/CAS configuration-sync patch is still excluded from this integration and kept separately on `feat/oss-multinode-config-sync`.
- **OSS Guardrails** - This fork's OSS build gains a built-in `guardrails` plugin that mirrors the enterprise Guardrails contract for a v1 subset: Secrets Detection over the embedded Gitleaks v8.30.1 rule set, in-process Custom Regex (RE2), and the Microsoft Presidio Analyzer. Actions are `detect_only`, `block`, and `redact`; `redaction_mode` is `runtime`; strategies are `replace`, `mask`, and `hash`; `target` is `llm` with `apply_to: input`, so responses and streams are not scanned and MCP tool traffic is not a target. Rule fields outside that subset (`output_mode`, `input_timing`, `evaluation_mode`, `profile_execution_mode: chained`, `stream_replay_event_interval_ms`, other `apply_to` or `target` values, other `redaction_mode` values) are rejected with HTTP `400` instead of being ignored, and a block answers HTTP `400` with error type `guardrail_intervention` without echoing matched text.
- **Guardrails Storage** - New `guardrail_providers` and `guardrail_rules` config store tables (SQLite and PostgreSQL, deliberately without an `enterprise_` prefix) hold profiles and rules, and `guardrails_config` in `config.json` and `bifrost.guardrails` in Helm reconcile into them by `config_hash` the same way routing rules do.
- **Guardrails API and UI** - `/api/guardrails/*` serves provider and rule CRUD, provider verification, the Gitleaks rule catalog, and a rule toggle endpoint; the dashboard's Guardrails pages are ordinary OSS pages, and incidents are read from the existing logs API through the `guardrail_outcomes` filter. A blocked request's logged input carries placeholders instead of the values it was refused for.
- **Gitleaks Dependency** - Secrets Detection pulls in the Gitleaks `detect` package and roughly 60 transitive modules (`mholt/archives`, brotli, sevenzip, rardecode, viper, cobra, lipgloss). Expect a larger binary and a wider supply-chain surface.
- **Fork-Only Guardrails Extensions** - `POST /api/guardrails/presidio/supported-entities` lets the gateway fetch the Analyzer's entity catalog for Analyzers a browser cannot reach, Presidio profiles accept `fail_open` (default `false`) to log a warning and forward unscanned traffic when the Analyzer fails, and `hash` redaction uses HMAC-SHA256 keyed from the deployment encryption key instead of a bare hash, falling back to a random per-process key when no encryption key is configured.
- **Guardrails Docs** - The enterprise Guardrails pages, the Presidio integration page, and the `config.json` and Helm guardrails guides carry a fork warning that scopes this build to the v1 subset and documents the fork-only options.
